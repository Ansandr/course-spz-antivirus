Рекомендована послідовність виконання курсового проекту.

| № | Етап | Результат | Практичні заняття за етапом роботи |  |
| ----- | ----- | ----- | ----- | ----- |
| 1 | Отримати і затвердити завдання. | Зафіксована тема у викладача | 1 заняття |  |
| 2 | Створення публічного репозиторію на GitHub згідно інструкції. Репозиторій має мати README.md файл орієнтовно до 600-800 символів. Файл має містити короткий високорівневий опис розробки включаючи до 10 функцій, які має реалізовувати програмне рішення. Цей файл має бути доданий окремою транзакцією через pull request затверджений викладачем. | Лінк на репозиторій у викладача на електронній скринці |  |  |
| 3 | Розробка вимог до програмного рішення.  | Затверджений текстовий документ requirements.doc на GitHub | 1 заняття |  |
| 4 | Розробка текстового опису дизайну програмного рішення, який включає:   високорівневий опис реалізації майбутнього програмного рішення згідно розроблених вимог; структуру програмного рішення; архітектуру класів, їх призначення і взаємодію; опис функцій; першу спробу реалізації каркасу програмного рішення з ієрархіями класів і їх членами, але без тіла методів (наприклад розробка \*.h файлів); цей каркас нівякому разі не розцінюється як остаточний і однозначно буде мінятися пізніше при реалізації програмного рішення.  Цей документ є проміжним і призначений для глибшого розуміння роботи, яку треба зробити, а також як відправна точка роботи над запискою до КП. На цьому етапі можна розробити UML діаграми. | Затверджений текстовий документ design.doc на GitHub | 1 заняття |  |
| 5 | Виділення окремих задач з обов’язковою оцінкою часу виконання. Це необхідно для того, щоб зорієнтуватися з функціоналом, який ви зможете реалізувати, щоб вкластися в задані терміни. Цей опис має бути у форматі user story \[1-2\]. Виконання кожної user story передбачає написання коду, відлагодження, тестування (написання юніт тестів \[4\], і тестів загалом \[5\] вітається, але не є необхідною для зарахування КР як виконаної, проте кожна user story має бути вами протестована, щоб впевнитися в тому що вона працює так як треба), оновлення документації (включно з розділами записки до КП), тому це треба врахувати при виставлені оцінок. | Текстовий документ stories.doc на GitHub.  На першій сторінці Має бути зміст з лінками на кожні user story. Одна user story на сторінку. | 1 заняття |  |
| 6 | Реалізація програмного рішення з використанням GitHub репозиторіїв, для зберігання коду і відмічанням user stories, які виконані. Ще раз, наявність юніт тестів вітається. | Код на GitHub | 4 заняття |  |
| 7 | Всі дефекти, які ви виявили в процесі тестування і не виправили мають бути задокументовані \[3\] і викладені у excel файлі на GitHub. | Текстовий документ defects.doc на GitHub.  На першій сторінці Має бути зміст з лінками на кожен дефект. Однин дефект на сторінку. Кожен дефект має бути описанй як розповідається у \[3\]. |  |  |
| 8 | Якщо ви все правильно зробили, то на даному етапі у вас має бути готова програма і записка до курсової роботи, так як вона є частиною дакументації, яку ви має оформляти при виконанні кожної user story. | Готова записка і код у вас у репозиторії на GitHub. |  |  |
| 9 | Викласти архів з кодом, скомпільований проект і записку на ВНС, щоб отримати оцінку. | Готова записка до курсового проекту у форматі pdf на ВНС. Код у архіві на ВНС. |  |  |
| 10 | Захист роботи. Роботу можна захищати поетапно під час виконання роботи показуючи і обговорюючи проект по частинах, затверджуючи проміжні етапи. | Оцінка у відомості |  |  |

Для затвердження документів рекомендовано відкривати “pull request” з робочої гілки до основної і надсилати лінк на “pull request” викладачу для погодження. Після отримання схвалення викладачем і об’єднання робочої гілки з основною  документ/код/будь що вважається затвердженим.
