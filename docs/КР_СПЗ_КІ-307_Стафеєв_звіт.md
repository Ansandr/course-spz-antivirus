[]{#_Toc232112052 .anchor}Анотація

У курсовому проекті розроблено програмне забезпечення для захисту
персональних комп\'ютерів від вірусів та шкідливих програм -
антивірусний сканер «Antivirus MVP» для операційної системи Windows.
Робота виконана за результатами аналізу п\'яти існуючих рішень (Windows
Security, ESET, ClamWin, rkhunter, System Informer), що дозволив виявити
дефіцит легких, прозорих та контрольованих користувачем інструментів
захисту.

Програму реалізовано мовою C++ 17 із застосуванням фреймворку Qt 6
Widgets за модульною архітектурою: низькорівневе ядро бізнес-логіки
оформлене у вигляді статичної бібліотеки, рівень представлення - у
вигляді GUI-застосунку. Реалізовано сигнатурне сканування файлів на
основі MD5-хешування (QCryptographicHash, QDirIterator), перегляд
активних процесів системи через Windows API (CreateToolhelp32Snapshot),
ізоляцію виявлених загроз до карантину, генерацію текстових звітів,
потоко-безпечне журналювання та підтримку білого списку виключень.
Тривалі операції виконуються в окремому потоці (QThread), що забезпечує
реагуючий інтерфейс.

Розробку організовано за методологією Scrum (14 User Stories, 3 спринти,
19 Story Points) із використанням системи контролю версій Git за
стратегією Gitflow. Працездатність підтверджено набором із 12
тест-кейсів, що покривають функціональні та нефункціональні вимоги;
коректність виявлення загроз перевірено за допомогою стандартного
тестового файлу EICAR.

## Огляд методів виявлення шкідливого програмного забезпечення

Проблема захисту від шкідливого ПЗ вирішується багатошаровим гібридним
підходом, оскільки жоден окремий метод не забезпечує достатню
ефективність. Основні методи:

Сигнатурний аналіз - порівняння файлів із базою відомих вірусних
сигнатур. Переваги: швидкість, точність. Недоліки: неефективний проти
невідомих загроз.

Евристичний аналіз - розпізнавання підозрілого поведінкового коду на
основі статичного аналізу. Виявляє поліморфні віруси, що видозмінюють
себе.

Поведінковий моніторинг - відстеження дій процесів у реальному часі
(читання файлів, системні виклики, мережева активність). Дозволяє
блокувати загрози нульового дня.

Хмарна репутація - централізований аналіз невідомих файлів та їх оцінка
на основі глобальної телеметрії мільйонів комп'ютерів.

## Аналіз існуючих програмних аналогів

Для обґрунтування необхідності розробки було проаналізовано п\'ять
різних рішень для захисту від шкідливого ПЗ, що представляють різні
підходи та цільові аудиторії.

### Вбудований захист Windows Security

Опис: Вільний, інтегрований у Windows 10/11 антивірус корпорації
Microsoft. Використовує сигнатури, евристику, машинне навчання та
компонент Smart App Control для оцінки репутації програм.

Переваги: Безплатний, безшовна інтеграція з ОС, мінімум конфліктів,
постійні оновлення.

Недоліки: Smart App Control блокує безпечні портативні програми без
дорогих цифрових сертифікатів; слабкість механізму Tamper Protection;
монополізація системних ресурсів Antimalware Service Executable.

### Програмний комплекс ESET

Опис: Комерційне преміум-рішення з евристичним аналізом та технологією
LiveGrid для хмарної репутації файлів.

Переваги: Висока швидкість реакції на нові загрози, низьке споживання
ресурсів, комплексний інструментарій (шифрування, батьківський
контроль).

Недоліки: Критична проблема - SSL-фільтрація за замовчуванням розриває
з\'єднання npm, pip та Git через самопідписаний сертифікат; надмірна

## Обґрунтування мети та завдань курсового проєкту

Аналіз п\'яти рішень виявив системну проблему сучасної антивірусної
індустрії: кожен інструмент проектується як моноліт з заздалегідь
визначеною філософією, жертвуючи гнучкістю заради спеціалізації.

Кумулятивні недоліки аналогів:

- Автоматичні системи (Windows Security, ESET) перевищують контроль
  користувача й блокують легітимний код;

- Open-source рішення (ClamWin) не мають моніторингу у реальному часі;

- Спеціалізовані інструменти (rkhunter, System Informer) недоступні для
  рядових користувачів (CLI, відсутність автоматизації);

- Всі рішення постійно генерують хибні спрацьовування або ускладнюють
  легітимну роботу розробників;

- Немає простого, легкого, прозорого рішення, що поєднує переваги.

Запропоноване рішення: Розробити легкий, модульний антивірусний сканер з
ясним UI, що поєднує:

- Сигнатурний аналіз з динамічним завантаженням баз;

- Евристичний модуль для виявлення поліморфних загроз;

- Моніторинг активних процесів у реальному часі;

- Мінімальне споживання ресурсів;

- Повна прозорість механізмів рішень (log-файли, деталізація);

- Ручний контроль користувача над автоматизацією.

## Технічне завдання

### Найменування та область застосування

**Назва проекту:** Модульна система виявлення та моніторингу шкідливого
програмного забезпечення на базі Windows.

**Область застосування:** Розробка легкого, контрольованого
антивірусного сканера для персональних комп\'ютерів з операційною
системою Windows 10/11, призначеного як для рядових користувачів, так і
для системних адміністраторів та розробників ПЗ.

###  Мета та завдання розробки

**Мета:** Створити прозорий, легкий антивірусний сканер з графічним
інтерфейсом на базі Qt/C++, що реалізує сигнатурне сканування файлів,
перегляд активних процесів та ізоляцію загроз у карантин, з повним
контролем користувача над всіма діями програми.

**Основні завдання:** 1. Розробити модуль сигнатурного аналізу: обхід
директорії, обчислення MD5-хешу кожного файлу та порівняння з локальною
базою signatures.db; 2. Реалізувати вікно перегляду активних процесів
системи (PID, ім'я, шлях до бінарника); 3. Розробити модуль карантину:
переміщення виявлених загроз до ізольованої директорії з можливістю
відновлення або видалення; 4. Розробити графічний інтерфейс (Qt Widgets)
з вкладками: Сканування, Процеси, Карантин, Журнал; 5. Реалізувати
логування всіх операцій програми у файл antivirus.log; 6. Підготувати
демонстраційну базу сигнатур з EICAR-тестовим файлом.

### Характеристика предметної області та обґрунтування необхідності розробки

За результатами аналізу п'яти провідних рішень виявлено критичний
дефіцит на ринку: - Комерційні антивірусні комплекси (ESET, Windows
Security) обмежують контроль користувача або порушують працездатність
легітимних засобів розробки; - Open-source рішення (ClamWin) не мають
моніторингу у реальному часі та виглядають архаїчно; - Спеціалізовані
інструменти (rkhunter, System Informer) недоступні для рядових
користувачів або потребують глибоких технічних знань.

Запропоноване рішення має заповнити цю нішу збалансованим, прозорим,
контрольованим інструментом з можливостями професійного рівня та
простотою використання для звичайних користувачів.

### Функціональні вимоги до системи

#### Функційність модуля сканування

**ВР1-Сканування:** Програма повинна виконувати сканування обраної
директорії з порівнянням MD5-хешів файлів з локальною базою сигнатур. -
Детально: Через кнопку "Обрати директорію" (стандартний QFileDialog)
користувач вибирає папку; запускається рекурсивний обхід (QDirIterator);
для кожного файлу обчислюється MD5-хеш через QCryptographicHash; хеш
порівнюється з signatures.db; результати (чисто/загроза) відображаються
у таблиці QTableWidget; прогрес показує QProgressBar; після завершення -
рядок зі статистикою (перевірено/знайдено загроз).

**ВР2-Карантин:** Програма повинна переміщувати виявлені загрози до
ізольованої директорії карантину. - Детально: При виявленні загрози та
підтвердженні користувача програма переміщує файл через QFile::rename()
до директорії %APPDATA%\\AntivirusMVP\\Quarantine\\; у вкладці
"Карантин" відображається список ізольованих файлів (ім'я, оригінальний
шлях, дата ізоляції); для кожного запису доступні кнопки "Відновити" та
"Видалити назавжди".

**ВР3-Перегляд процесів:** Програма повинна відображати список всіх
активних процесів системи. - Детально: Вкладка "Процеси" показує таблицю
з колонками: PID, Ім'я процесу, Шлях до виконуваного файлу; список
отримується через Windows API CreateToolhelp32Snapshot() /
Process32First() / Process32Next(); кнопка "Оновити" оновлює список; для
підозрілих процесів (не мають цифрового підпису або шлях у Temp)
підсвічується рядок червоним кольором.

**ВР4-Звітування:** Програма повинна записувати результати сканування у
текстовий файл. - Детально: Після завершення сканування програма
автоматично зберігає звіт у
%APPDATA%\\AntivirusMVP\\Reports\\scan_YYYYMMDD_HHMMSS.txt; звіт
містить: дату/час, кількість проаналізованих файлів, список виявлених
загроз з повними шляхами та MD5-хешами; кнопка "Відкрити звіт" відкриває
файл у стандартному текстовому редакторі.

**ВР5-Білий список:** Програма повинна підтримувати список виключень зі
сканування. - Детально: У вкладці "Налаштування" є текстове поле для
додавання шляхів-виключень (по одному на рядок); список зберігається у
%APPDATA%\\AntivirusMVP\\whitelist.txt; перед скануванням кожного файлу
перевіряється, чи його шлях не входить до виключень - якщо так, файл
пропускається.

**ВР6-Журналювання:** Програма повинна вести журнал усіх операцій у
текстовий файл. - Детально: Усі події (запуск сканування, знаходження
загрози, переміщення до карантину, помилки читання файлів) записуються
до %APPDATA%\\AntivirusMVP\\antivirus.log з часовою міткою та рівнем
(INFO / WARNING / ERROR); вкладка "Журнал" завантажує та відображає
вміст файлу через QPlainTextEdit; реалізується через singleton-клас
Logger.

####  Функційність модуля інтерфейсу

**ВР7-Графічний інтерфейс:** Програма повинна мати зрозумілий графічний
інтерфейс на Qt Widgets з чотирма вкладками. - Детально: Головне вікно
QMainWindow містить QTabWidget з вкладками: "Сканування" (вибір
директорії, прогрес, таблиця результатів), "Процеси" (таблиця активних
процесів), "Карантин" (список ізольованих файлів), "Журнал" (текстове
поле з логом) та "Налаштування" (білий список); всі тривалі операції
виконуються у QThread, щоб UI залишався реагуючим.

### Нефункціональні вимоги до системи

#### Вимоги до продуктивності

**НВ1-Швидкість сканування:** Час сканування одного типового файлу
(розмір 1 МБ) не повинен перевищувати 50 мс. - Обґрунтування: Дозволяє
завершити повне сканування типової домашньої папки (100 ГБ, \~100 тис.
файлів) протягом \~1.5 години при фоновому режимі.

**НВ2-Утилізація CPU:** Під час фонового сканування програма не повинна
утилізувати більше 25% CPU однієї ядра. - Обґрунтування: Не перешкоджає
основній роботі користувача при відкритих браузерах, редакторах та інших
застосунків.

**НВ3-Утилізація пам'яті:** Резидентна утилізація оперативної пам'яті не
повинна перевищувати 150 МБ у звичайному режимі. - Обґрунтування:
Залишає достатньо ресурсів для комфортної роботи користувача на системах
з 8 ГБ оперативної пам'яті.

**НВ4-Час відповіді інтерфейсу:** Час відповіді на дії користувача
(клацання кнопок, прокручування) не повинен перевищувати 100 мс. -
Обґрунтування: Забезпечує плавний та реагуючий користувацький досвід.

#### Вимоги до надійності та безпеки

**НВ5-Надійність:** Програма не повинна вихід з ладу при обробці
пошкоджених або аномальних файлів. - Обґрунтування: Повинна мати обробку
виключень для всіх потенційно небезпечних операцій (читання файлів,
парсинг структур); критична помилка не повинна призвести до краху
програми.

**НВ6-Захист від втручання:** Программа повинна захищатися від спроб
вирусів видалити або модифікувати її файли. - Обґрунтування: Виконуваний
файл програми та файли конфігурації повинні встановлюватися з
обмеженнями доступу; мають перевірятися цифрові підписи всіх критичних
компонентів.

**НВ7-Конфіденційність:** Програма не повинна збирати та передавати дані
про користувача без його явної згоди. - Обґрунтування: Всі операції
сканування, логування та оновлення баз виконуються локально; хмарні
функції (якщо реалізовані) активуються тільки після явного підтвердження
користувачем.

### Допущення та обмеження

#### Допущенн

- Користувач має права адміністратора на своєму комп'ютері для
  встановлення програми та запуску драйверів;

- Комп'ютер має стабільне мережне з'єднання для завантаження оновлень
  баз (мінімум 1 Мбіт/с);

- База вірусних сигнатур розпорядника буде оновлюватися щомісяця з новим
  контентом;

- Не враховуються атаки користувача з правами TrustedInstaller або
  спеціальні техніки ескалації привілеїв;

- Програма розроблюється як рішення для захисту кінцевих точок (endpoint
  protection), а не для централізованого корпоративного управління.

#### Обмеження

- Функціональність за межами проекту (виключена зі скоупу MVP):

  - Автоматичне планування сканувань за розкладом - відсутній
    планувальник задач;

  - Блокування запуску підозрілих процесів у реальному часі - відсутній
    драйвер рівня ядра (minifilter);

  - Мережеве оновлення бази сигнатур - база оновлюється вручну заміною
    файлу;

  - Інтеграція з контекстним меню Windows Explorer;

  - Евристичний аналіз вмісту файлів (тільки хеш-порівняння);

  - Інтеграція з централізованими системами керування (SIEM, EDR);

  - Мобільна версія для Android або iOS;

  - Міжплатформна портативність (Linux, macOS).

- Технічні обмеження:

  - Програма не може запуститися на пошкоджених або зараженим системах,
    де критичні компоненти ОС вже скомпрометовані;

  - Не гарантується виявлення 100% сучасних руткітів, що мають більш
    глибоку інтеграцію з ядром, ніж сама програма;

  - Евристичний аналіз базується на статичних ознаках файлу, без
    використання динамічної пісочниці (sandbox) або машинного навчання.

- Вимоги до персоналу:

  - Адміністратор/розробник повинен розумітися на основах Windows API та
    архітектури процесів;

  - Для налаштування конфіг-файлів потрібна базова грамотність у роботі
    з текстовими файлами та реєстром Windows.

ProcessList, Logger, ReportWriter. Компілюються як статична бібліотека
antivirus_core.lib, що забезпечує незалежність бізнес-логіки від GUI. -
**Рівень представлення (GUI)** - клас MainWindow на Qt Widgets, що
підключає бібліотеку ядра та відображає результати.

### Модуль SignatureDB

Клас SignatureDB завантажує базу сигнатур у QHash\<QString, QString\> -
хеш-таблицю з O(1)-пошуком. Формат файлу signatures.db: кожен рядок -
MD5_HEX ThreatName; рядки, що починаються з #, ігноруються як коментарі.

*// signaturedb.cpp*\
bool SignatureDB::load(const QString& filePath) {\
QFile file(filePath);\
**if** (!file.open(QIODevice::ReadOnly \| QIODevice::Text))\
**return** **false**;\
\
static const QRegularExpression ws(R\"(\\s+)\");\
QTextStream in(&file);\
**while** (!in.atEnd()) {\
const QString line = in.readLine().trimmed();\
**if** (line.isEmpty() \|\| line.startsWith(\'#\')) **continue**;\
const QStringList parts = line.split(ws, Qt::SkipEmptyParts);\
**if** (parts.size() \>= 2)\
m_signatures.insert(parts.at(0).toLower(),\
parts.mid(1).join(\' \'));\
}\
**return** !m_signatures.isEmpty();\
}\
\
QString SignatureDB::lookup(const QString& md5Hex) const {\
**return** m_signatures.value(md5Hex.toLower());\
}

### Модуль Scanner

Scanner успадковує QObject для роботи з QThread. Рекурсивний обхід
виконується через QDirIterator, MD5-хешування - через
QCryptographicHash. Атомарний прапор std::atomic\<bool\> m_running
дозволяє безпечно зупинити сканування з GUI-потоку без mutex.

*// scanner.cpp - метод run() (виконується у QThread)*\
void Scanner::run() {\
m_running.store(**true**);\
\
*// Pre-count файлів для точного QProgressBar*\
int total = 0;\
QDirIterator counter(m_directory,\
QDir::Files \| QDir::NoSymLinks, QDirIterator::Subdirectories);\
**while** (counter.hasNext()) { counter.next(); ++total; }\
\
int current = 0, threats = 0;\
QDirIterator it(m_directory,\
QDir::Files \| QDir::NoSymLinks, QDirIterator::Subdirectories);\
\
**while** (it.hasNext() && m_running.load()) {\
const QString filePath = it.next();\
emit progress(++current, total);\
\
*// Перевірка whitelist (вимога ВР5)*\
bool skip = **false**;\
**for** (const QString& wl : std::as_const(m_whitelist))\
**if** (filePath.startsWith(wl, Qt::CaseInsensitive))\
{ skip = **true**; **break**; }\
**if** (skip) **continue**;\
\
const QString md5 = computeMd5(filePath);\
**if** (md5.isEmpty()) {\
emit logMessage(\"WARNING\", \"Cannot open: \" + filePath);\
**continue**;\
}\
**if** (m_db) {\
const QString threat = m_db-\>lookup(md5);\
**if** (!threat.isEmpty()) {\
++threats;\
emit threatFound(filePath, threat, md5);\
}\
}\
}\
emit finished(current, threats);\
}

ProcessList використовує Windows API tlhelp32.h. Для кожного процесу

## База сигнатур та демонстраційний файл EICAR

Для тестування системи використовується стандартний EICAR-тест-файл
(European Institute for Computer Anti-Virus Research). Його MD5-хеш є
публічно відомим та включений до signatures.db:

\# signatures.db - формат: MD5_HEX ThreatName\
44d88612fea8a8f36de82e1278abb02f EICAR-Standard-Test-File

EICAR-тестовий рядок (абсолютно нешкідливий, стандартизований):

X5O!P%@AP\[4\\PZX54(P\^)7CC)7}\$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!\$H+H\*

Збереження цього рядку у файл .txt або .com і запуск сканування тієї ж
директорії дозволяє перевірити правильність виявлення без використання
реального шкідливого коду.

## Стратегія тестування

### Мета та підхід

Метою тестування є підтвердження відповідності розробленого програмного
забезпечення функціональним вимогам ВР1--ВР7 та нефункціональним вимогам
НВ1--НВ10, визначеним у попередніх розділах пояснювальної записки.

Згідно з тест-планом (test-cases.md), застосовано трирівневу стратегію
тестування:

- **Модульне тестування (Unit-testing)** --- проводиться з використанням
  фреймворку Qt Test для перевірки окремих компонентів системи
  (SignatureDB, Scanner, Quarantine). Метою є верифікація коректності
  бізнес-логіки незалежно від графічного інтерфейсу.

- **Інтеграційне тестування (Integration testing)** --- виконується
  шляхом ручного тестування графічного інтерфейсу користувача відповідно
  до тест-кейсів TC-01--TC-12. Перевіряється взаємодія між основними
  підсистемами (сканування, карантин, GUI, журналювання, обробка
  процесів).

- **Регресійне тестування (Regression testing)** --- здійснюється після
  внесення змін та виправлення дефектів шляхом повторного виконання
  релевантних тест-кейсів (зокрема TC-04, TC-05, TC-08).

Такий підхід дозволяє забезпечити повне покриття як логіки роботи
системи, так і її інтеграції в умовах реального використання.

### Тестові дані

Для перевірки функціональності використовувалися репрезентативні тестові
дані:

- **EICAR-тестовий файл** (eicar.com.txt) --- стандартний тестовий рядок
  антивірусних систем, що дозволяє перевірити механізм виявлення загроз.
  Відповідний MD5-хеш присутній у базі сигнатур (*signatures.db*).

- **Тестові директорії**:

  - порожня директорія --- для перевірки граничних умов;

  - директорія з великою кількістю файлів --- для перевірки
    продуктивності та реакції GUI;

- **Білий список (whitelist.txt)** --- містить шляхи, які повинні
  виключатися зі сканування;

- **Заблокований файл** (locked.dat) --- використовується для перевірки
  обробки помилок доступу (ризик Р1).

### Критерії успішності тестування

Тестування вважається успішним за виконання наступних умов:

- всі критичні тест-кейси (TC-01, TC-04, TC-11) виконані успішно;

- всі тест-кейси TC-01--TC-12 пройдені без дефектів, що блокують
  функціональність;

- критичні та високопріоритетні дефекти виправлені;

- дефекти середнього та низького рівнів задокументовані як відомі
  обмеження системи.

## Виявлені дефекти

У процесі тестування виявлено та задокументовано критичного пріоритету.

1.  **Дефект BUG-01**

**Назва:** некоректна активація кнопки відкриття звіту

**Вимога:** ВР4-Звітування

Проблема полягала у тому, що після примусової зупинки сканування кнопка
відкриття звіту залишалася неактивною. Причиною було те, що сигнал
завершення сканування не генерувався у випадку переривання процесу.

Дефект було виправлено шляхом коректного опрацювання сигналу завершення
та підтверджено повторним виконанням тест-кейсу TC-08.

[]{#_Toc232112101 .anchor}Висновки

У ході виконання курсового проєкту розроблено програмне забезпечення для
захисту від вірусів та шкідливих програм - «Antivirus MVP» - відповідно
до технічного завдання, сформульованого у розділі 2.1.

**Виконані завдання:**

1.  Розроблено модуль сигнатурного аналізу на базі
    QCryptographicHash::Md5 та QDirIterator; реалізовано завантаження
    бази хешів у QHash\<QString,QString\> з O(1)-пошуком.

2.  Реалізовано перегляд активних процесів системи через Windows API
    CreateToolhelp32Snapshot() / QueryFullProcessImageNameW() з
    коректною обробкою ERROR_ACCESS_DENIED.

3.  Розроблено модуль карантину: ізоляція файлів через QFile::rename(),
    збереження метаданих у quarantine_index.json, відновлення та
    видалення.

4.  Реалізовано п'ятивкладковий графічний інтерфейс на Qt 6 Widgets
    (QMainWindow, QTabWidget); тривале сканування виконується у QThread,
    GUI залишається реагуючим.

5.  Розроблено потоко-безпечний Singleton-логер (QMutex, RAII),
    генератор текстових звітів та підтримку білого списку виключень.

6.  Підготовлено демонстраційну базу сигнатур із EICAR-тестовим файлом.

Розробку організовано за Scrum-методологією: 14 User Stories, 3 спринти,
19 Story Points. Управління версіями - Git Gitflow, репозиторій
опублікований на GitHub.

Архітектурні рішення, структура класів та логіка алгоритмів розроблені
автором самостійно. GitHub Copilot (модель Claude Sonnet 4.6)
використовувався як асистент: генерація шаблонного коду Qt (підключення
сигналів/слотів, компонування віджетів), шаблонів документації (User
Stories, тест-кейси) та рефакторинг фрагментів коду. Весь вміст
пояснювальної записки, технічне завдання та архітектурні рішення
опрацьовано та перевірено автором.
